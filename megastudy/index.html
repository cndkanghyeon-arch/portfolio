화면 기획과 운영 정책을 같이 쥐는 자리입니다

공고에서 확인한 사실

  • 학원 운영을 받치는 웹과 앱, 백오피스를 함께 기획하고 운영합니다
  • 요구사항을 분석해 기능 명세서와 화면 설계서를 직접 씁니다
  • 신규 기획만이 아니라 기존 서비스의 사용성과 전환율 개선이 업무에 들어 있습니다
  • 상담과 예약, 결제 같은 서비스 정책과 운영 프로세스를 정의합니다
  • 개발과 디자인, 운영 조직을 오가며 커뮤니케이션합니다
  • 우대사항에 초기 구축과 리뉴얼, 수강신청과 예약, 결제, CRM, 관리자 시스템 기획이 들어 있습니다

그래서 생기는 문제와 제 접점

  • 웹과 앱, 백오피스를 따로 기획하면 정책이 세 벌로 갈라집니다. 저는 가입과 결제 정책을 한 벌로 두고 앱 안에 iframe으로 태우는 구조를 기획해 가입과 매출을 각각 30% 올렸습니다
  • 전환율은 화면을 예쁘게 고쳐서 오르지 않습니다. 저는 어디서 몇 명이 빠지는지부터 보고 흐름 자체를 바꿔 예약 노쇼를 40%에서 20%로 내렸습니다
  • 결제는 정상 경로보다 예외 경로에서 사고가 납니다. 저는 PG 중복 콜백을 재현해 원인을 특정하고 멱등키 기반 차단 구조를 설계해 중복 결제를 없앴습니다
  • 백오피스는 요청받은 대로 버튼을 늘리면 금세 못 쓰게 됩니다. 저는 반복 요청을 유형으로 묶어 기능으로 흡수시켜 개발 요청을 약 80% 줄였습니다
  • 조직 사이의 말은 문서가 아니라 산출물로 맞춥니다. 저는 화면기획서와 정책정의서, IA, ERD, API 명세를 직접 쓰면서 다섯 개 팀 14명과 일했습니다

고치기 전에 어디서 끊기는지부터 셉니다

화면을 바꾸는 일은 대개 마지막에 합니다.

Step 01

이탈 지점을 숫자로 특정한다

불편하다는 말은 어디가 불편한지 알려 주지 않습니다. 운영 데이터와 CS 기록에서 사람이 실제로 빠지는 구간을 먼저 찾고, 거기만 건드립니다.

Step 02

예외 경로를 정책으로 먼저 닫는다

정상 흐름은 누구나 그립니다. 중복 요청과 실패 재시도, 취소와 환불처럼 어긋나는 경로를 정책정의서에 먼저 적고 화면 설계서를 씁니다.

Step 03

반복 요청은 기능으로 흡수시킨다

같은 요청이 세 번 들어오면 개별 처리를 멈추고 백오피스 기능으로 올립니다. 운영이 개발 대기에 묶이지 않아야 기획이 다음 일을 할 수 있습니다.
